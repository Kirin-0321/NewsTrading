# 任务流间隔调度使用说明

## 🎯 功能介绍

**间隔调度**允许任务流每隔固定时间自动执行一次，适合需要持续监控的场景。

### 两种调度模式对比

| 模式 | 说明 | 示例 | 适用场景 |
|------|------|------|----------|
| **daily** | 每天固定时间执行 | 每天09:30 | 每日晨会前分析 |
| **interval** | 每隔N小时执行 | 每1小时 | 盘中实时追踪 |

### 方法2：在代码中使用

```python
from core.workflow_engine import get_workflow_engine

# 获取引擎
engine = get_workflow_engine()

# 启动间隔调度（每1小时执行一次）
engine.start_interval_schedule('enhanced_news_flow', interval_hours=1)

# 或者每2小时执行一次
engine.start_interval_schedule('enhanced_news_flow', interval_hours=2)

# 或者每30分钟执行一次（需要自己实现分钟级调度）
```

## ⚙️ 配置说明

### 配置文件格式

编辑 `workflows/configs/enhanced_news_flow.json`：

```json
{
  "schedule": {
    "enabled": false,              // 是否启用（目前interval模式不使用此字段）
    "mode": "interval",            // 模式: daily 或 interval
    "time": "09:30",              // daily模式使用：固定时间
    "interval_hours": 1,          // interval模式使用：间隔小时数
    "description": "定时执行模式说明"
  }
}
```

### 模式详解

#### 模式1：daily（每天固定时间）
```json
{
  "schedule": {
    "enabled": true,
    "mode": "daily",
    "time": "09:30"
  }
}
```
- 每天早上9:30自动执行
- 适合：每日例行分析

#### 模式2：interval（每隔N小时）
```json
{
  "schedule": {
    "mode": "interval",
    "interval_hours": 2
  }
}
```
- 每隔2小时自动执行
- 适合：盘中实时追踪

## ⚠️ 注意事项

### 1. 执行时长vs间隔时间
- 如果任务执行时长 > 间隔时间，会导致任务堆积
- 建议：间隔时间 ≥ 任务平均执行时间 × 2

**示例**：
- 任务平均执行时间：3分钟
- 建议间隔：≥ 1小时（有充足缓冲）

### 2. 资源占用
- 长时间运行会占用系统资源
- 建议定期重启（如每天凌晨）

### 3. API限额
- 频繁调用AI API可能超限额
- 建议：
  - 1小时间隔：适中
  - 2小时间隔：保守
  - 4小时间隔：经济

### 4. 数据累积
- 原始文件会不断累积
- 建议定期清理 `data/raw/` 目录

### 5. 程序必须保持运行
- 关闭程序或终端会停止调度
- 后台运行方案：
  - Windows服务
  - Linux screen/tmux
  - Docker容器

## 🔧 故障排查

### 问题1：间隔时间不准确
**原因**：程序被阻塞或系统休眠
**解决**：
- 检查是否有长时间运行的任务
- 确保系统不进入休眠状态

### 问题2：执行失败后停止
**原因**：异常未捕获
**解决**：
- 查看日志文件
- 检查网络连接
- 验证API配置

### 问题3：占用内存过高
**原因**：长时间运行内存泄漏
**解决**：
- 定期重启程序（如每天一次）
- 使用监控工具自动重启

### 问题4：想修改间隔时间
**方法1**：停止后重新启动，输入新的间隔时间
**方法2**：在代码中动态修改
```python
schedule.clear('enhanced_news_flow')
engine.start_interval_schedule('enhanced_news_flow', interval_hours=新的小时数)
```

## 💡 最佳实践

### 1. 推荐的间隔时间

| 场景 | 推荐间隔 | 理由 |
|------|---------|------|
| 盘中实时追踪 | 1小时 | 及时捕捉新闻，不会过于频繁 |
| 日常监控 | 2-4小时 | 平衡时效性和资源消耗 |
| 轻度使用 | 6-12小时 | 减少API调用和成本 |

### 2. 参数优化建议

**高频执行（1小时）**：
```json
{
  "params": {
    "crawler": {
      "scroll_times": 20,      // 减少滚动
      "auto_stop": true        // 启用自动停止
    },
    "export": {
      "time_range_hours": 2    // 只导出最近2小时
    },
    "merger": {
      "mode": "recent",
      "recent_count": 3        // 只合并最近3个文件
    }
  }
}
```

**低频执行（4小时+）**：
```json
{
  "params": {
    "crawler": {
      "scroll_times": 50,      // 增加滚动
      "auto_stop": false       // 关闭自动停止，爬取更多
    },
    "export": {
      "time_range_hours": 12   // 导出更长时间范围
    },
    "merger": {
      "mode": "all"            // 合并所有文件
    }
  }
}
```

### 3. 组合使用

**方案A**：工作日间隔执行 + 每日固定分析
- 工作日9:00-18:00：每2小时执行（间隔调度）
- 每天收盘后15:30：执行一次完整分析（daily调度）

**方案B**：多实例运行
- 实例1：每1小时，快速分析（小参数）
- 实例2：每天晚上，深度分析（大参数）
