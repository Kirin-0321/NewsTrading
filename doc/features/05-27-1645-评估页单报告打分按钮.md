## 一、动机

主人手动跑了一份 backtest 报告（id=96, 14 题材），评估页却 **0 行**。
诊断发现：

| 表 | 行数 |
|----|------|
| `ai_reports` | 3 |
| `theme_predictions` | 14（全在 id=96 那份）|
| **`theme_prediction_scores`** | **0** ← 评估页 SQL 起手就 JOIN 这张表 |

原 `get_template_eval` / `get_report_eval` SQL：

```sql
FROM theme_prediction_scores tps      ← scores 0 行 → 输出必然 0 行
JOIN theme_predictions tp ON tp.id = tps.theme_id
```

主人原话："**默认加载全部已经抽取过的报告，每一个报告后都添加一个打分按钮**"。

## 二、设计要点（主人决策记录）

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 「过滤」默认范围 | **所有 ai_reports**（含未抽题材的）| 主人要看全貌，孤儿报告也应该看到 |
| 「打分」按钮粒度 | **3 态**：none / partial / full | 信息量高，颜色文字双重提示 |
| CLI 工具 | **新增 `tools/score_one_report.py`** | CLI-first 原则，GUI/CLI 对齐 |
| md 物理删除 | （沿用前次 `overwrite` 决策） | 保持文件系统与 db 一致 |

## 三、改动一览

### 3.1 后端（`services/scoring/scoring_service.py`）

#### `get_report_eval` 重写 SQL

```sql
FROM ai_reports ar                              ← 主表换成 ai_reports
LEFT JOIN per_theme ON per_theme.report_path = ar.file_path
WHERE ar.report_date >= ? {extra}
GROUP BY ar.id
```

每行新增 4 字段：

| 字段 | 含义 |
|------|------|
| `report_id` | `ai_reports.id`（按钮回调用）|
| `themes_count` | 该报告 theme_predictions 实际行数 |
| `scored_pairs` | 已写入 scores 的 `(theme, score_date)` 对数 |
| `expected_pairs` | `themes_count × 5`（理论应打数）|
| `score_status` | `"none"` / `"partial"` / `"full"` |

#### `get_template_eval` 重写 SQL

```sql
FROM theme_predictions tp                       ← 主表换成 theme_predictions
LEFT JOIN theme_prediction_scores tps ON tps.theme_id = tp.id
WHERE tp.report_date >= ? {extra}
GROUP BY tp.prompt_id [+ version]
```

每行新增字段：

| 字段 | 含义 |
|------|------|
| `themes_total` | 该模板下题材总数（含未打）|
| `scored_themes` | 至少有一行 scores 的题材数 |
| `sample_count` | 兼容老字段 = `themes_total` |

#### 新增 `rescore_one_report(report_id)` API

```python
def rescore_one_report(
    report_id: int, *, days_back: int = 5, ...
) -> BatchScoringResult:
    """按 ai_reports.id 单报告打分，不波及其他报告。"""
```

实现：查 `ai_reports.file_path` → 反查 `theme_predictions WHERE report_path = ?`
→ 对每个 theme_id 跑 `score_theme_on_date` D+1~D+5（`force_full_window=True`）。

#### 顺手修一个隐藏 bug

旧 SQL 用 `tps.{time_dim} >= ?` cutoff 传 `YYYYMMDD` 8 字符，但
`theme_prediction_scores.report_date` 实际是 `YYYY-MM-DD` 10 字符（继承自
`theme_predictions`）。字符串比较 `'20260520' < '2026-05-20'`（`'0'` 48 vs
`'-'` 45）造成 `time_dim=report_date` 模式的过滤永远失效。新版按字段格式
分别用 `cutoff_dash` 与 `cutoff_compact`，并在 fixture 中对齐生产数据格式
（`_yyyymmdash_back`）。

**下表新增 2 列**：

|---|------|-----|

## 四、调用链

```
评估页加载
  ├── get_template_eval(time_dim=report_date)   → 上表（含未打分模板）
  └── get_report_eval(time_dim=report_date)     → 下表（含未打分报告）
                                                  + score_status / 按钮文字

下表「打分」按钮点击
  └── _on_score_clicked(report_id)
        └── RescoreWorker(report_id=report_id)
              └── scoring_service.rescore_one_report(report_id)
                    ├── SELECT ai_reports + theme_predictions
                    └── for each theme:
                          for sd in _eligible_score_dates(...):
                              score_theme_on_date(theme_id, sd, write=True)
                                → INSERT OR REPLACE INTO
                                  theme_prediction_scores
        finished_result.emit({mode:"one_report", ...})
              → _on_rescore_done → refresh()
```

CLI 等价：

```bash
python tools/score_one_report.py --report-id 96
python tools/query_eval.py --by report --time-dim report_date
```

### 6.2 已知限制

1. **「参数一致性」仅按 `(prompt_id, report_date)`**：news 窗口不入判定，
   后续如需精细区分可扩 `ai_reports` 表加 `news_window_hash`
2. **孤儿报告**（id=11 / id=65 `theme_extracted=1` 但 0 题材）会以
   "✗ 无题材" 灰按钮出现，按钮 disable；要清理需手动 `DELETE`
3. **`score_date <= report_date` 字符串比较**：`script_scorer.py` 第 147
   行 `if score_date <= report_date` 当 score 是 YYYYMMDD（8 字符）而
   report 是 YYYY-MM-DD（10 字符）时，因 `'0'` > `'-'` 始终 false，
   防穿越保护失效。本次未修，但 fixture 已对齐，未来单独 ticket 修
4. **没改 `run_daily_scoring`**：默认调度仍按区间扫所有题材，单报告 API
   仅 GUI/CLI 主动调用
