## 一、改了什么

把手动回测页从「一次只能跑一条」改为：

* **连点 N 次「正式跑回测」就排 N 个任务进队列**，后台同时跑 3 个，其余排队
* **新增「任务列表」**位于「时间边界预览」右半（横向 splitter 平分）
* **点任务列表行 → 下方流式 / md 预览 / 题材表三块联动切换**
* dry-run 试算同样走队列（执行快、不调 LLM）
* 删除按钮：仅终态任务可删；**只删 GUI 行，不动 md/db**（产物清理是评估页的事）

### 改造前

```
点跑 → "已有一个在跑，请等它完成" ← 不能连点

```

```
4 条任务 8 并发 ≈ 全部并行 60s = 约 1 分钟（21:35 hotfix 后）
```

**总耗时压缩到 1/2~1/3。**

## 四、并发安全设计

### race 风险与修复

发现一处隐患：worker 的 `progress / streaming / finished_result / finished` 信号
默认 `connect(lambda...)` 时，**lambda 在 worker 子线程被调用**。如果直接在
lambda 里改 `self._running` / `self._pending` / `self._pump()`，多 worker 同
时完成时会引发 race（重复起 worker / 漏起）。

**修复**：manager 内部加 6 个 `_relay_*` 信号，lambda 只做 `emit relay`，
relay 接到 manager 自身槽。manager 是主线程对象，AutoConnection 检测跨
线程后自动用 `QueuedConnection`，所有状态修改严格在主线程事件循环串行
执行。

### 验证

`case_01_concurrency_limit`（5 任务 3 并发，显式注入）+ `case_09_fifo_order`
（4 任务按 FIFO 进出）+ `case_11_default_concurrency_is_8`（10 任务默认 8）
实测无并发问题。

## 六、并发数演进（3 → 8）

### 21:00 初版决策：固定 3

主人勾选「固定 3」。当时理由：

1. **DeepSeek 限流阈值**：免费档 60 req/min，付费档更高。每次手动回测约 1~2
   个 LLM 请求，3 并发 ≈ 6 req/min，远低于阈值
2. **SQLite WAL 写并发**：已实测 CLI `--workers 4` 跑 30 天历史无错，3 更稳
3. **主人交互预期**：3 个并发跑足够覆盖"调 prompt 时对比模板/日期"场景

### 21:35 hotfix：默认提到 8

主人实测 3 并发跑得顺，要求"能不能更多路"。第一性重评：

| 维度 | 8 并发评估 |
|---|---|
| SQLite WAL 写并发 | CLI workers=4 实测过，5~8 完全扛得住 |
| DeepSeek 限流 | 付费档实测可稳定 60+ req/min；8 并发 ≈ 16 req/min，远低于阈值 |
| Provider 偶发 5xx | 单笔失败概率轻微上升，但失败只影响单个 task，不污染其他 |
| 主人体验 | 8 路并跑 = 1 分钟跑完 8 个回测，调 prompt 工作流大幅加速 |

**结论**：8 是个稳的上限；再高（≥12）DeepSeek 偶发 502 概率开始非线性增加。

### 实施

* `gui/workers/manual_backtest_manager.py`：`_DEFAULT_MAX_CONCURRENT = 8`
* `__init__` 加 `max_concurrent: Optional[int] = None` 参数（用于回归测试
  显式注入 3，保留原有 5 任务 / 3 并发的语义验证）
* page UI 5 处提示文案"3 并发" → "8 并发"
* 回归测试新增 `case_11_default_concurrency_is_8`（10 任务默认上限 8）

### 仍然不开放给 GUI 调

主人选了 "B 不动 UI" 形态。如果将来还想再调（5/12/...），改类常量
`_DEFAULT_MAX_CONCURRENT` 一行；不需要走 GUI。
