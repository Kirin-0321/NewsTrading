# 05-26 22:30 — 盘后数据近 7 天补全 + 后端 4 字段派生

## 背景

GUI 板块行情 Tab 改为「Top 20 / Bottom 10」后，主人发现 Top 11~20 与 Bottom
全段的「5 日」「涨停」「龙头股」「催化」四列均为 `—`。诊断后定位到：

| 字段 | 缺失根因 |
|---|---|
| `pct_chg_5d` | `_enrich_sector_5d_pct` 只对当日 Top 10 算（10/486 板块有数据） |
| `limit_up_count` | `fact_limit_stock.theme` 来自 `kpl_list`，但后端 `_read_sectors_top` 直接读 `fact_sector_daily.limit_up_count`，而该列**整列全 NULL**（tushare_fetcher 注释"M1b 留空"未兑现） |
| `leaders` | `_read_sectors_top` 写死 `leaders: []`，注释"M2 阶段填充"未兑现 |
| `catalysts` | `cls_enricher` / `ai_enricher` 仅对 `top_sector_n=10` 注入，Top 11~20 无 |

## 改动

### 新增
- **后端 `MarketSummaryService._derive_sector_leaders`** — 从 `fact_limit_stock`
  按 `theme LIKE '%板块名%'` 派生 `(limit_up_count, leaders)`；leader 字段对齐
  `renderer._format_leader` 期望 `{name, pct_chg, status, cons_nums}`
- **GUI `market_db_helper._derive_sector_leaders`** — 与后端同口径的私有 helper，
  供 `query_sectors_extended` 给 Top 11~20 / Bottom 10 也补 leaders+limit_up_count
- **`doc/updates/05-26-2230-盘后数据近7天补全.md`**（本文件）

### 优化
- **`tushare_fetcher._enrich_sector_5d_pct(top_n)`** —
  默认改为 `top_n=0`（全板块）。`dc_daily` 接口本来就拉全板块，只是写回时按
  top_codes 过滤。改全量后 fact_sector_daily.pct_chg_5d 覆盖从 **10/486 → 460/486**，
  零 API 成本，仅多数百次 UPDATE（毫秒级）
- **`MarketSummaryService._read_sectors_top`** — 调用 `_derive_sector_leaders` 后
  写入 `limit_up_count`、`leaders` 字段；同时 `field_sources` 也标记派生来源
- **`gui/utils/market_db_helper.query_sectors_extended`** — Top/Bottom 段都补
  leaders+limit_up_count；docstring 同步更新
- **`gui/workers/market_fetch_worker.py`** — 默认 `top_sector_n: 10 → 20`
- **`gui/pages/schedule_page.py`** — task 字典默认 `top_sector_n: 20`
- **`services/market/tushare_fetcher._enrich_sector_5d_pct`** — 调用方
  `fetch(top_sector_n=N)` 内显式传 `top_n=0`（与 top_sector_n 解耦）

### 修复
- 截图反馈的 Top 11~20 / Bottom 10 板块「5 日」全 `—` 问题（pct_chg_5d 已覆盖
  到全板块）
- `sectors_top[].leaders` / `sectors_top[].limit_up_count` 长期为空数组的
  M2 阶段 TODO

## 已知问题

### 1. `limit_up_count` / `leaders` 命中率仅 ~15%

**根因**：数据源天然不对齐
- `fact_limit_stock.theme` 来自 Tushare `kpl_list` 接口，是顿号分隔的
  组合串（"先进封装、先冲封装"、"AI硬件、通信"、"成长股、元宇宙"）
- `fact_sector_daily.name` 来自 Tushare `dc_index` 接口，是细分概念名
  （"EDA概念"、"MLCC"、"存储芯片"、"高带宽内存"）
- 两套命名口径不一致，单向 `theme LIKE '%板块名%'` 只能命中
  名称恰好是 theme 子串的少数板块

**已接受的折中**：
- 后端 + helper 都用统一的 LIKE 匹配，能命中就命中
- 未命中板块返回 `limit_up_count=None / leaders=[]`，GUI 显示 `—`
- 不做多对多映射表（工程量大，收益边际递减）

### 2. 20260526 当日 0 命中

`kpl_list(trade_date=20260526)` 接口返回 0 行，所以 fact_limit_stock.theme
全 NULL → 任何 LIKE 都匹配不到。这是 Tushare 数据延迟，T+1 后会补齐。

### 3. Bottom 10 板块 `leaders` 几乎都是 0

弱势板块本来就没涨停股，是预期行为（`leaders` 取的是涨停股代理）。

## 影响面

- **GUI 板块行情 Tab**：Top 20 + Bottom 10 都会显示「5 日」「催化」列；
  Top 段约 15% 板块显示「涨停数」「龙头股」
- **CLI 评估 / Markdown**：`renderer._build_sectors_top` 硬编码 `sectors[:10]`，
  AI prompt 长度不变；但 `sectors_top[].leaders` 已经有数据，Markdown 里
  「龙头股」列会从「—」变成「{name}({状态})」格式
- **AI 评估 token**：增量约 +10~30 字符/天（leader 名串），可忽略
- **DeepSeek AI 调用**：每天 2 次 → 仍是 2 次（cls 兜底数量不变，
  unmatched 板块数量 5~10 个仍走单次 AI 批处理）
- **Tushare API 调用**：每天 +1 次（多了 `_enrich_sector_5d_pct` 全板块
  的 1 次 dc_daily 调用？不，那个本来就 1 次，没变；总数还是 20 次/天）
