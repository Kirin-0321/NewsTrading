## 二、技术选型

### 2.1 自检方式

抽象统一 helper（避免 14 处重复样板）：

```python
# services/market/tushare_fetcher.py
def _table_has_data(self, table: str, trade_date: str) -> bool:
    """检测某 fact 表在某交易日是否已有数据（用于逐表幂等跳过）。"""
    with self.db.connect(readonly=True) as conn:
        row = conn.execute(
            f"SELECT 1 FROM {table} WHERE trade_date = ? LIMIT 1",
            (trade_date,),
        ).fetchone()
    return row is not None
```

每个 step 在自身函数最前面插一行检测：

```python
def _fetch_index_daily(self, result):
    if not result.force_refresh and self._table_has_data(
        "fact_index_daily", result.trade_date
    ):
        result.skipped.append("fact_index_daily")
        return
    # ... 原逻辑 ...
```

为此 `FetchResult` 增加 `force_refresh: bool` 字段，从 `fetch()` 入参传递进来。

### 2.2 `fact_limit_stock` 特殊策略

主人钦点「默认强制重拉」。落地方式：
- 在 step 4 进入前**统一 DELETE** 当日 `fact_limit_stock`（无视 force_refresh 标记）
- step 4/5/6 顺序 `INSERT OR REPLACE` 写入（PK 冲突自动覆盖）
- step 8 的 `_fetch_kpl_prev` 写 `prev_trade_date`，同样在进入前 DELETE 该 prev_date 的 limit 行

代码上抽一个 `_purge_limit_stock(trade_date)` helper，被 4 处复用。

### 2.3 第 15 步：`_fetch_stock_daily`

复用现成的 `services.market.stock_daily_sync.sync_stock_daily`（已具备幂等、防穿越、INSERT OR REPLACE）：

```python
def _fetch_stock_daily(self, result):
    if not result.force_refresh and self._table_has_data(
        "fact_stock_daily", result.trade_date
    ):
        result.skipped.append("fact_stock_daily")
        return
    from services.market.stock_daily_sync import sync_stock_daily
    res = sync_stock_daily(
        result.trade_date,
        db=self.db,
        client=self.client,
        force=result.force_refresh,
    )
    if not res.ok:
        result.warnings.append(
            f"sync_stock_daily 失败: {res.error}"
        )
    else:
        result.ingested["fact_stock_daily"] = res.rows_written
```

### 2.4 service.build() 缓存命中分支改造

旧逻辑（service.py:243-250）：

```python
if not force_refresh:
    cached = self.get(td)
    if cached.ok:
        cached.from_cache = True
        return cached            # ← 直接返回，绕过 fetcher
```

新逻辑：

```python
if not force_refresh:
    cached = self.get(td)
    if cached.ok:
        progress("命中缓存，开始补齐缺失维度…")
        # ✅ 仍跑一次 fetcher：force_refresh=False 让 14+1 个 step 自检
        try:
            self.fetcher.fetch(
                trade_date=td,
                prev_trade_date=cached.prev_trade_date or "",
                top_sector_n=top_sector_n,
                force_refresh=False,
                progress_callback=progress,
            )
        except Exception as exc:
            result.warnings.append(f"缓存命中后补缺失败: {exc}")
        cached.from_cache = True
        cached.elapsed_ms = int((time.time() - t0) * 1000)
        return cached
```

绝大多数情况下 14+1 个 step 都会自检命中（毫秒级 COUNT），只有真缺的维度才真正调 API。

### 2.5 完整度评分纳入 `fact_stock_daily`

两步走：

**a) summary 构造时新增字段 `breadth.stock_daily_rows`**

在 `service._build_summary_from_db()` 拼 `breadth` 节点处加一行 SQL：

```python
breadth["stock_daily_rows"] = self._count_stock_daily_rows(td)
# = SELECT COUNT(*) FROM fact_stock_daily WHERE trade_date=?
```

**b) schema 加一项**

`config/market_summary_schema.json` 的 `fields` 节点新增：

```json
"breadth.stock_daily_rows": {
  "layer": "L1", "weight": 2, "required": true
}
```

validator 已经支持 schema-driven，自动生效。

### 2.6 取消 fetcher 一刀切早退

直接删除 `tushare_fetcher.py:158-167`：

```python
elif self._has_index_data(trade_date):  # ← 整段删
    result.skipped.append("all")
    return result
```

`_has_index_data` 函数本身保留（向后兼容用），但 `fetch()` 主流程不再用它。

### 2.7 `_purge_trade_date` 扩展

`tables` 列表新增 `fact_stock_daily`。

```python
if not result.force_refresh and self._table_has_data("fact_X", result.trade_date):
    result.skipped.append("fact_X"); return
```


## 五、风险登记

| # | 风险 | 影响 | 缓解措施 |
|---|------|------|---------|
| R1 | `fact_limit_stock` 4 个 step 中某个失败但前面已 DELETE，导致 limit 表「数据丢失一半」 | 中 | 在 fetcher.fetch() 顶层加事务封装？SQLite 多步事务复杂，**降级策略**：step 4/5/6/8 中任一步抛异常，warning 入 result.warnings，主人重按一次按钮即可恢复（force 重拉本身就是 idempotent） |
| R2 | step 15 调 daily 失败（API 限流/超时），导致全部个股 Tab 仍为空 | 中 | sync_stock_daily 本身有 try-except 返回 `ok=False`，本步走 warning 不阻塞主流程；主人下次按钮重试即可 |
| R3 | schema 加新字段后旧 summary（已入库的 market_summaries 行）评分会变低 | 低 | 旧行本来就是历史快照，不重算；只对新生成的 summary 生效 |
| R4 | 缓存命中场景下跑 fetcher 让"秒级缓存"变慢 | 低 | 实测 15 次 COUNT(*) < 50ms 在 SSD 上；如果 14+1 都 skip，整体仍接近秒级 |
| R5 | `fact_limit_stock` 默认重拉会浪费 4 次 API 调用 | 低 | 主人已知情接受；后续 P1 可考虑给表加 `src` 字段做细粒度自检（不在本轮） |
| R6 | `_has_index_data` 早退被删后，所有按按钮场景都会进入 14+1 个 step 自检循环 | 低 | 自检本身只是 14 次 COUNT，无副作用 |

## 七、回滚策略

2. **手动应急**：主人临时跑 `python tools/sync_daily_market.py --trade-date YYYYMMDD` 补齐 fact_stock_daily（与现有逻辑兼容）
