## 一、是什么

> 一句话：**手动回测页改成"连点 N 次跑按钮排 N 个任务进队列，后台同时跑 3 个，点哪个任务看哪个"**。

UI 形态（沿用现有页面，只在中间一块改造）：

```
┌─ 回测参数（不动）─────────────────────────────────────────────┐
│ 模板 / 交易日 / 精选 / 新闻窗左右 / Provider / 跑按钮…         │
└──────────────────────────────────────────────────────────────┘
┌─ ⏱ 时间边界预览  |  📋 任务列表 （新增：横向 splitter）──────┐
│  trade_date         │ # 模板        日期      状态     用时 ⛔  │
│  新闻窗 / 上限       │ 1 scalper   20260522  ✅ 完成  38.2s 🗑  │
│  实际新闻数         │ 2 custom_6  20260523  ⏳ 跑中  12.5s 🗑  │←
│  snapshot 完整      │ 3 custom_6  20260524  ⌛ 排队   --   🗑   │点击行
│  D+1~D+5            │ 4 ds_pro    20260525  ❌ 失败  3.1s  🗑   │联动切换
└──────────────────────────────────────────────────────────────┘
┌─ 下方三大块（不动布局，内容跟着选中任务联动切换）─────────────┐
│ 🤖 AI 流式输出 / 📄 md 预览 / 🎯 题材表                        │
└──────────────────────────────────────────────────────────────┘
```

跟现在比，关键差异就 2 条：

1. **再也不会"已有一个回测在跑，请等它完成"**——主人想连点几次就连点几次，全部进队列
2. **后台同时跑 3 个**（固定 3，给 LLM provider 留出限流缓冲），剩下的乖乖排队等

## 二、为什么做（用户情景）

### 主人当前的痛点

> 主人原话："手动回测一次测一条太慢，能不能改成可以多开并行"

实际跑数据看，**一条手动回测耗时 30~60 秒**（LLM 推理本身就慢），主人调一个新 prompt 时常要：

- 跑同一个模板在 3~5 个不同交易日，看打分曲线
- 跑同一个交易日下 2~3 个不同模板，对比哪个抽题材准
- 想看连板高潮日 + 中位震荡日 + 低迷日各跑一次，对比表现

**当前 GUI 一次只能跑一条**，跑 5 次就得在椅子上枯坐 3~5 分钟，主人喷"太慢"很合理。

### 为什么不直接喊主人用 CLI？

辉夜检查了一下，**`tools/backtest_prompt.py --workers 4` 早就支持并发**，是 GUI 单方面做了"一次一条"的限制。

但主人坚持要 GUI 能并行，理由也很合理：

1. **CLI 黑窗口看不到 LLM 流式输出**——只能盯着 `.` 一个个打出来，不知道生成了什么
2. **临时改一下时间窗、换个模板**，GUI 点几下就行，CLI 得拼一长串参数
3. **看结果反查**——GUI 已经有"点开 md / 题材表联动"的现成体验，CLI 跑完得自己去 `data/AI_analysis/...` 翻文件

所以方向是：**不动 CLI，让 GUI 也享受到后端早就准备好的并发能力**。

### 不做会怎样

主人继续骂"太慢"，每次调 prompt 都要花十几分钟实际是在等串行排队。  
辉夜继续被骂，强迫症发作（明明后端能并发，GUI 故意拦着……忍不了）。

## 三、具体要求

### A. 形态决策（主人已勾选）

| # | 决策点 | 主人选择 | 理由（辉夜补） |
|---|---|---|---|
| 1 | 并行的产品形态 | **任务队列 + 三大块联动展示**（不是多 Tab） | 充分利用「时间边界预览」右边的死空白，UI 改动量最小 |
| 2 | 后台并发数 | **固定 3** | 保守但够用，避开 DeepSeek 限流；连点 10 个也只同时跑 3 个，剩下排队 |
| 3 | 任务列表的列 | **# / 模板 / 日期 / 状态 / 用时 / ⛔ 删除按钮** | 删除列让主人能"跑错参数立刻撤" |
| 4 | 默认选中策略 | **自动选中"最新提交"的任务** | 主人刚点完跑就能立刻看到它的流式输出 |
| 5 | 任务列表清理 | **不主动清理，加滚动条** | 跑多了自动滚，关掉 GUI 自动清空 |

### B. 行为约束（辉夜补的硬性需求）

1. **每个任务的内存独立**——chunk / 阶段日志 / 完成 md / 抽到的题材，全部存在任务对象里，互不污染
2. **切换任务必须无延迟**——点列表行 → 下方三块立即整段回灌（包括正在跑的任务，从开始到当前的全部 chunk）
3. **运行中任务也能点别的看**——当前正在跑的任务不被打断，主人切去看任务 #2 不会让任务 #1 停下来
4. **关 GUI 不留垃圾**——任务不持久化，关闭/重启清空（手动回测本来就是 ad-hoc 调试用）
5. **dry-run 也算任务**——dry-run 试算同样走队列，状态机里能区分（虽然它跑得快）
6. **状态机**：`排队中 ⌛` → `运行中 ⏳` → `完成 ✅` / `跳过 ⏹` / `失败 ❌`
7. **删除时**：如果任务正在跑——禁用删除（避免半截删 GUI 状态紊乱）；任务已完成的——只删 GUI 行，**不动产出（md/db）**（删数据库的事归「评估页·单报告删除」按钮管）

### C. 必须排除的东西

- ❌ **不做多窗口 / 多 Tab**——PyQt5 单 GUI 实例，开新窗口性价比极低；任务列表足够直观
- ❌ **不做任务持久化**——手动回测就是 ad-hoc，跑过的报告本来就进了 `ai_reports` 表，不需要 GUI 再存一份"任务历史"
- ❌ **不做暂停/恢复**——LLM 调一半难暂停，加这功能等于谎话；删除就是完全等价的取消（其实也只是从 UI 拿掉，跑出来的还是入了库）
- ❌ **不动 CLI 接口**——CLI 已经能并发，本次纯 GUI 改造
- ❌ **不开放并发数给主人调**——主人勾的就是"固定 3"；将来要调改个常量就行，不暴露 UI 控件

## 四、预期效果

### 主人的工作流（改造后）

```
1. 在「回测参数」选好模板A + 日期1
2. 点「正式跑回测」     ← 任务#1 进队列，立即开跑
3. 改成模板A + 日期2
4. 再点「正式跑回测」   ← 任务#2 进队列，立即开跑（并发数 2/3）
5. 改成模板B + 日期1
6. 再点「正式跑回测」   ← 任务#3 进队列，立即开跑（并发数 3/3 满）
7. 改成模板B + 日期2
8. 再点「正式跑回测」   ← 任务#4 进队列，但要等 #1/#2/#3 跑完一个才轮到
9. 喝口茶 → 60 秒后 #1 跑完，#4 自动开始
10. 主人点任务列表里的 #2 → 下方流式区切到 #2 的实时 chunk
11. 看到 #2 跑得不对劲（题材抽错了）→ 主人不删，让它跑完看结果
12. 主人点 #4（还在排队中）→ 下方空白提示"⌛ 排队中"
13. 主人点完成的 #1 → 下方显示完整 md + 题材表
14. 跑完一轮 4 个 ≈ 80~90 秒（vs 当前必须 4×60 = 240 秒）
```

**核心收益**：4 个任务从 4 分钟 → 1.5 分钟，**总耗时压缩到 1/2~1/3**（取决于并发数）。

### 视觉效果（关键 UI 反馈）

- **状态颜色染色**：⌛ 排队中（灰）/ ⏳ 运行中（蓝）/ ✅ 完成（绿）/ ⏹ 跳过（橙）/ ❌ 失败（红）
- **当前选中行高亮**：QTableWidget 自带行选中色，下方三块就跟着切
- **运行中任务的"用时"会自增**：每秒刷新一次"已跑 X.X s"，让主人能看出"这条卡了"
- **删除列**：🗑 emoji 图标按钮，点击直接删行；正在跑的任务图标 disable（灰化）

## 六、Q&A

### Q1: 同时跑 3 个任务，DB 写入会冲突吗？

A: 不会。`backtest_one` 内部每次新建 `AnalysisService` / `TushareClient` 实例，写 SQLite 走 WAL 模式（已开），多线程并发写已实测过——CLI `--workers 4` 跑过 30 天历史无错。

### Q2: 同时跑 3 个 LLM 请求，会被 DeepSeek 限流封号吗？

A: DeepSeek API 的免费档约 60 req/min，付费档更高。手动回测一次大约 1~2 个 LLM 请求（分析 + 题材抽取），3 并发约等于 6 req/min，远低于限流阈值。**保守起见才选固定 3，不开放主人调。**

### Q3: 流式输出 chunk 跑在哪个线程？切换任务会不会丢字？

A: 每个 worker 在自己的 QThread 里跑，chunk 通过 Qt 信号到主线程（GUI 线程），主线程把 chunk **同时**：
- 写入"该任务的内存缓冲区"（不论是不是当前选中）
- 如果当前选中的就是这个任务，再 append 到 stream_browser

切换任务时：清空 stream_browser → 整段回灌新任务的缓冲区 → 后续 chunk 继续 append。**不丢字、不污染、不卡顿。**

### Q4: 跑了 5 个任务后关 GUI 再开，能看到上次的吗？

A: 看不到。任务对象是 GUI 进程内的内存对象，关 GUI 就没。但**实际产出（md 文件 + ai_reports 行 + theme_predictions 行）都已入库**，去「模板评估页」查得到。

### Q5: 如果一个任务跑挂了（LLM 超时/网络断），会拖累其他任务吗？

A: 不会。每个 worker 独立，单个失败只影响它自己，其他 worker 该跑跑该排排。失败任务的 error 字符串会保留到任务对象里，主人点它能看到错误详情。

### Q6: dry-run 是不是也可以全部勾完一键试算？

A: 是。dry-run 走同一个队列，但因为不调 LLM，每个 dry-run 只 100~300ms，3 并发跑 10 个 ≈ 1 秒全完事，比串行体验更好。

### Q7: 为啥不直接做"批量勾选模板 × 多日期"那种笛卡尔积？

A: 那是另一个产品形态（需要新 UI 控件 + 多选 + 范围日期选择器），跟"连点 N 次"是两条平行路径。本次先做"连点 + 队列"——它是更通用的底层能力，将来要做"批量勾选"也只是在它之上加个壳。**不一次做完，避免一个 PR 改一堆地方。**
