## 一、为什么要先把时间边界讲清

一次"虚拟回测"涉及多个时间维度互相牵动；任何一个错位都会导致：

| 错位场景 | 实际后果 |
|---------|---------|
| `report_date` 写成今天 | GUI「按日期筛选」看不到回测样本 / 评估页混乱 |
| `news_end_dt` 超过 next_open 09:00 | 穿越（看了下一周期新闻 → 评分作弊） |
| `market_summary_date` 晚于 news_end_dt 16:00 | 穿越（用了未来盘后数据） |
| `score_date ≤ trade_date` | 用回测日当天行情打回测日的预测分（看了答案） |
| 新闻窗口太短 | 新闻样本少 → AI 题材抽取空 → 0 题材入库 |

所以本文档把 **每一个时间** 的定义、来源、默认值、合法范围、互相约束钉在一个
地方，后续 GUI / CLI / 文档都引用本文。

## 三、关键决策表

### 3.1 默认窗 helper（**主人语义**）

```
compute_default_news_window(trade_date) →
    news_start_dt = trade_date 14:00
    news_end_dt   = next_trade_date(trade_date) 09:00
```

| 场景 | trade_date | 默认 news_start_dt | 默认 news_end_dt（= 硬上限） |
|------|------------|---------------------|------------------------------|
| 周一 | 5/25 | 5/25 14:00 | 5/26 09:00 |
| 周五 | 5/22 | 5/22 14:00 | **5/25 09:00**（跨周末） |
| 周二 | 5/26 | 5/26 14:00 | 5/27 09:00 |
| 节假日前最后开市日 | 5/30（假设节后 6/3 开市） | 5/30 14:00 | **6/3 09:00**（跨节假日） |

### 3.2 `market_summary_date` 推导表（v2）

> 来源：`services/scoring/snapshot.py::_resolve_market_summary_date`

| 条件 | `market_summary_date` |
|------|--------------------|
| `trade_date` 开市 且 `news_end_dt ≥ trade_date 16:00` | `trade_date`（当天盘后已结算） |
| `trade_date` 开市 但 `news_end_dt < trade_date 16:00`（早盘视角） | `pretrade_date` |
| `trade_date` 非交易日（周末/节假日） | `pretrade_date` |
| 缓存缺日历且 `client=None` | `None`，`missing_reason` 标注原因 |

### 3.3 防穿越铁律（snapshot.py 已强校验）

1. **左 < 右**：`news_start_dt < news_end_dt`，否则抛 `SnapshotError`
2. **右 ≤ 硬上限**：`news_end_dt ≤ next_trade_date(trade_date) 09:00`，
   否则抛 `SnapshotError(... 硬上限 ...)`
3. **新闻窗内所有新闻 < `news_end_ts`**：兜底 assert 防数据脏污
4. **盘后日期 16:00 时间戳 ≤ `news_end_ts`**：自动选 trade_date 当天或前一交易日
5. **回测窗不在未来**：`backtest_one` 入口校验 `news_end_dt ≤ now`
6. **打分日期 > report_date**：`scoring_service` 用 `pairs_succeeded` 失败统计反映

## 四、举例对照主人新语义

### 4.1 周五 5/22 默认窗（跨周末到周一开盘）

```
输入:
  trade_date    = "20260522"  (周五)
  news_start_dt = None         (→ 默认 5/22 14:00)
  news_end_dt   = None         (→ 默认 5/25 09:00，next_trade_date)
  news_status   = "curated"    (默认)

推导:
  news 时间窗            = [2026-05-22 14:00:00, 2026-05-25 09:00:00)
                          —— 整个周末的新闻都纳入
  实际命中 news_count    = 339（5/22 午后 + 5/22 夜间 + 周末 + 5/25 早 09 前）
  max_news_end_dt        = 2026-05-25 09:00:00  (← 已触上限)
  market_summary_date    = "20260522"
                          (5/22 开市 且 news_end_dt >= 5/22 16:00)
  market_summary_md      = market_summaries[5/22].summary_md

产物:
  ai_reports.report_date     = "2026-05-22"
  ai_reports.is_backtest     = 1
  ai_reports.file_path       = "data/AI_analysis/.../xxx_backtest_20260522.md"
  theme_predictions.*        = 同步透传

衍生:
  score_date(D+1) = "20260525" (周一)
  score_date(D+2) = "20260526" (周二)
  score_date(D+3) = "20260527" (周三)
  score_date(D+4) = "20260528" (周四)
  score_date(D+5) = "20260529" (周五)
```

### 4.2 周一 5/25 默认窗

```
输入:
  trade_date    = "20260525"  (周一)
  默认窗 = [5/25 14:00, 5/26 09:00)  ← next_trade_date 09:00 = 周二早

推导:
  实际命中 news_count    = 179
  max_news_end_dt        = 2026-05-26 09:00:00
  market_summary_date    = "20260525"
```

### 4.3 主人手动收窄右边界（早盘视角）

```
输入:
  trade_date    = "20260526"
  news_start_dt = datetime(2026, 5, 26, 9, 0)   (主人改成 9:00)
  news_end_dt   = datetime(2026, 5, 26, 10, 0)  (主人改成 10:00)

推导:
  news 时间窗            = [2026-05-26 09:00:00, 2026-05-26 10:00:00)
  market_summary_date    = "20260525"
                          (news_end_dt = 10:00 < 16:00 → 用前一交易日 5/25 盘后)

适用场景: 模拟"晨会研报"，只看开盘第一小时
```

### 4.4 主人故意触上限（应被拒）

```
输入:
  trade_date    = "20260522"  (周五)
  news_end_dt   = datetime(2026, 5, 26, 9, 0)   (主人想看到周二早 9:00)

结果:
  SnapshotError: news_end_dt(2026-05-26T09:00:00) 超过硬上限
                 (2026-05-25T09:00:00 = next_trade_date 09:00)，
                 不允许覆盖下下次开盘以后的新闻

  → 主人应该改 trade_date = "20260525" 才能用周二的窗
```

## 六、修复路径（已实施）

### 6.1 最小侵入方案（已实施）

只改 `tools/backtest_prompt.py::_run_analyze_and_mark_backtest`，详见源码。

不改 `analysis_service.py` 的理由：
1. analyze 是核心服务，被定时任务/GUI/CLI 三处复用，加 `report_date_override`
   参数会污染所有调用方
2. backtest_prompt 已经是 analyze 的"包装层"，事后修正符合关注点分离

### 6.2 备选：长期重构（不做）

将来若有第二个"非今日"场景（如重跑历史失败任务），再考虑给 `analyze` 增加
`report_date_override` 参数。当前不做。

### 6.3 `overwrite` 行为（v3 升级，2026-05-27 16:35）

`backtest_one(..., overwrite=...)` 命中 `_has_existing_backtest` 时的处理：

| `overwrite` | 行为 | 适用场景 |
|------------|------|----------|
| `False`（默认） | `skipped=True`，error 提示「传 --overwrite」 | 批量 `backfill_backtest_samples.py` ─ 避免重复浪费 LLM |
| `True` | 调 `_delete_existing_backtest`：删 `ai_reports` + `theme_predictions`（CASCADE 拖走 `theme_stocks` / `theme_news` / `theme_prediction_scores` / `theme_stock_scores`）+ 物理 md 文件，然后继续跑 | GUI 手动回测（默认勾选「已存在则覆盖」）+ 修复 bug 后重跑验证 |

**精确匹配范围**：仅 `(prompt_id, report_date, is_backtest=1)`。  
真实日常报告（`is_backtest=0`）**永远不会**被误删。

**返回字段**：`BacktestResult.overwritten / deleted_reports /
deleted_themes / deleted_md_files` 透传给 CLI 输出与 GUI status_label。

完整 bugfix 记录见 [手动回测覆盖语义](../bugfix/05-27-1635-手动回测覆盖语义.md)。

## 七、配套 CLI 工具

### 7.1 时间边界查验（`tools/snapshot_inspect.py`）

```bash
# 默认窗（主人推荐）：trade_date 14:00 → next_open 09:00

    --news-start 202605221400 --news-end 202605221600
```
