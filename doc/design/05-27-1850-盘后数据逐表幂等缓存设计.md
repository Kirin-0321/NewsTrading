# 功能设计·主人通读版：盘后数据「逐表幂等缓存」语义修订

> 阶段：✅ **已通过主人审核** → 见 [施工方案](./05-27-1900-盘后数据逐表幂等缓存施工方案.md)
> 主人决策：D1=B / D2=A / D3=C / D4=A / D5=B / `fact_limit_stock` 默认强制重拉
> 触发原因：当前缓存语义是「一刀切跳过」，导致按钮拉数据时部分表永远空着（如 `fact_stock_daily` 今日 0 行）

---

## 一、是什么

把「获取/重新获取」按钮的缓存语义，从「**整体命中就全跳**」改成「**逐项判断、缺啥补啥**」。

一图概括（用类比）：

```
旧语义（一刀切）：             新语义（逐项判断）：
┌─────────────────┐            ┌─────────────────┐
│ 14 个数据维度    │            │ 14 个数据维度    │
│  └─ 看老大有没有 │            │  ├─ 指数 ✅已有 → 跳 │
│     ✅老大有     │            │  ├─ 板块 ✅已有 → 跳 │
│     → 全部跳     │            │  ├─ 涨停 ❌缺  → 拉 │
│     ❌老大无     │            │  ├─ ……         │
│     → 全部拉     │            │  └─ 个股 ❌缺  → 拉 │
└─────────────────┘            └─────────────────┘
```

简单讲：以前是「班长签到了就当全班都签了」，现在是「每个人独立签到，谁缺就补谁」。

---

## 二、为什么做（用户情景）

### 痛点 1：今天的全部个股 Tab 显示「共 0 只」

主人今天（2026-05-27）按了「获取/重新获取」按钮，状态栏明明显示「✅ 完整度 95.6%」，但「全部个股」Tab 依然「共 0 只」。

根本原因：负责装填全 A 股个股日线的数据，**根本不在按钮的工作清单里**。它要靠「计划任务」里一个叫 `stock_daily_sync` 的独立模块去填——而那个模块只有在「定时任务」页面设置过、并实际跑过的情况下才会动。主人没设过 → 表永远空。

### 痛点 2：缓存语义僵化，「补缺」靠人工

即使主人忘了某个维度，按钮也帮不上忙——它现在的逻辑是「指数表有数据 = 整批已完成 = 不需要再问 Tushare 任何事」。一旦中间某天某个维度抓取失败、或者后续新增了维度（比如本次的全 A 股个股），就成了**永远填不上的洞**——除非主人勾「强制重拉」全表重抓（API 浪费 + 速度慢）。

### 痛点 3：完整度评分骗人

「完整度 95.6%」让主人以为数据基本齐了，但其实**全 A 股个股日线一行都没写**——这一项要么没被纳入评分公式，要么权重小到无感。

### 主人的实际使用场景

- 收盘后第一时间按「获取/重新获取」想看完整盘后
- 中途切到「全部个股」Tab 排查涨停股的同行情况
- 切板块时点「全部板块」Tab 想看完整 480 个板块的当日表现
- 每个 Tab 都该「按一次就齐」，不该让主人去翻定时任务设置

### 不做会怎样

主人每次想看「全部个股 Tab」都要去命令行手动跑 `tools/sync_daily_market.py`，体验割裂、容易忘、和「按钮即点即看」的初衷违背。AI 分析也拿不到全市场涨跌幅这一关键维度，导致后续题材打分 / 评分系统的上下文断层。

## 三、具体要求

### 必须包含

1. **按钮按下后，14 个维度的数据自动逐项检测：缺啥拉啥，已有的不重抓**
   - 已有维度跳过 → 节省 API 调用
   - 缺失维度拉取 → 保证数据完整

2. **新增「全 A 股个股日线」维度作为第 15 个数据项**
   - 接入按钮工作清单
   - 让「全部个股 Tab」与按钮形成闭环
   - 复用既有的同步函数（不重复造轮子）

3. **「强制重拉」勾选项的语义保持「彻底重抓」**
   - 包括第 15 项（全 A 股个股）也要被清空 + 重拉
   - 不留任何「漏网维度」

4. **缓存命中（按钮按了 2 次、第 2 次拿盘后总结）的场景也要顺手补缺**
   - 第 1 次按按钮：缺啥拉啥 + 写盘后总结
   - 第 2 次按按钮：盘后总结已存在 → 直接读出（保持秒级）
   - 但**同时也要顺手检查 14+1 项数据是否齐**，缺的补上（毫秒级 SQL 检测）

### 必须排除

1. **不动 dim_stock / dim_sector 等全局字典表的填充节奏**（字典每天都该刷新 last_seen_date，与 fact_* 表的「按交易日」语义不同）
2. **不改任何 fact_* 表的字段定义 / 索引结构**（纯流程改造，零结构变更）
3. **不动 AI 兜底（hybrid 模式的 CLS + AI 补全）的执行时机**——它仍然在数据拉齐之后跑

## 四、预期效果

### 主人能怎么用、看到什么

1. **早上开盘前** 按一次「获取/重新获取」（不勾 force）
   - 状态栏：「拉取指数 ✅ | 板块 ✅ | 涨停 ✅ | …… | 全 A 股个股 ✅ | 完整度 99%」

2. **晚上 7 点再按一次**（看 AI 兜底是否还有更新）

   - 速度仍接近秒级（绝大多数表都已齐，只跑 15 次 COUNT(*) 自检）

3. **怀疑数据有误想重抓** 勾「强制重拉」
   - 14+1 张 fact 表 + market_summaries 全部清空重写
   - 包括以前永远清不掉的全 A 股个股表

### 完整度评分修正

* 把「全 A 股个股」纳入评分维度
* 真实反映数据齐不齐，不再有「95.6% 但全部个股 Tab 空着」这种矛盾

## 六、Q&A（预想主人会问）

**Q1：14 个 step 每个都加自检，那 fetcher 是不是会臃肿？**
A1：自检是 1 行 SQL `SELECT COUNT(*) FROM fact_X WHERE trade_date=?` + 1 行 if 判断。14 个 step 每个就多 2 行，整体可控。本喵会抽象成统一 helper（这点放施工方案讨论）。

**Q2：fact_limit_stock 这张表被 4 个 step 共写（涨停/跌停/同花顺/昨日），自检会不会互相打架？**
A2：会，这是这次最大的坑。涉及"按 src（来源）维度判断"。如果主人勾「保留独立 step」可能要给 fact_limit_stock 加 src 字段，**这点需要施工方案阶段确认是否已有该字段**。如果没有，本轮可能要顺手补字段，或者把 4 个 step 合并成 1 个。

**Q3：「顺手补缺」会让原本秒级的缓存命中变慢吗？**
A3：会慢一点，但只是慢「15 次 COUNT(*) 查询」 + 「实际缺失维度的 API 拉取」。15 次 COUNT 在 SSD 上 < 50ms，无感。

**Q4：以后再加新维度（比如 daily_basic 换手率市盈率）容易接入吗？**
A4：容易。新 step 按本次模板照搬即可——加一个 fetch 方法、加一行自检、加一行 purge 表名。

**Q5：会不会破坏现有的板块表填充？**
A5：不会。板块表（fact_sector_daily）当前是按钮和计划任务**双轨**都能填，本次改造只是让按钮变得更聪明，计划任务路径不动。
