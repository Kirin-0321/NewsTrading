# 文档分类规范

> 定义 `doc/` 下文档的分类、目录与命名。新建文档必须遵守本规范。

---

## 目录结构

```
doc/
├── 文档分类规范.md    # 本文件（元规范，固定放根目录，不参与下文命名）
├── bugfix/
├── design/
├── features/
├── guides/
├── reports/
├── updates/
└── 其他/
```

| 目录 | 用途 |
|------|------|
| `bugfix/` | Bug 修复、排障、错误修正 |
| `design/` | 方案、架构、技术选型、接口设计 |
| `features/` | 功能说明、增强、实现细节 |
| `guides/` | 教程、手册、配置、FAQ |
| `reports/` | 分析、测试、审查、总结报告 |
| `updates/` | 版本更新、变更日志、迭代记录 |
| `其他/` | 未归类、临时、备忘 |

## 与 `.huiye/` 工作目录的边界

`.huiye/` 是辉夜的私有工作目录，**仅允许**存放以下四类（白名单）：

1. 角色规约 `soul.md`（正文已迁移至 [.cursor/rules/huiye-persona.mdc](../.cursor/rules/huiye-persona.mdc)，`.huiye/soul.md` 仅作旧链接兼容跳板）
2. 文档总索引 `README.md`（跨文档跳转、进度快照、TODO 全局视图）
3. `_` 前缀的临时草稿、调试快照、字段审计、迁移基线（用过即可删）
4. 跨多份正式文档的"汇总索引"——只放指向 `doc/` 的链接 + 一句话简介，**不重复正文内容**

**其余一切正式文档必须放 `doc/{子目录}/`**，按下文「命名规范」和「分类标准」组织。

判定流程：

```
新文档
  ├─ 属于「设计/功能/指南/bugfix/报告/更新/其他」之一？ → doc/{对应子目录}/
  └─ 属于「角色规约/总索引/_前缀草稿/汇总索引」之一？     → .huiye/
     其他情况 → 找用户确认
```

**禁止行为**：

- 把设计方案 / 施工方案 / 功能说明 / 评审报告以"它是项目必要文档"为由塞进 `.huiye/`
- 在 `doc/` 创建临时草稿（临时草稿一律放 `.huiye/_xxx.md`）
- 同一份文档在两边各放一份（正文只能在 `doc/`，`.huiye/README.md` 里放链接即可）

详细的判定与历史遗留处理见 [`.cursor/rules/huiye-persona.mdc` §记忆与文档归档](../.cursor/rules/huiye-persona.mdc)。

## 命名规范：月-日-时-简述

### 格式

```
MM-DD-TT-简述.md
```

即 **月-日-时分-简述**，四段、`-` 分隔：

| 段 | 含义 | 规则 |
|----|------|------|
| **MM** | 月 | 两位 `01`–`12` |
| **DD** | 日 | 两位 `01`–`31` |
| **TT** | 时分 | 24 小时制 **HHmm** 四位，如 `0930`、`1430`（不足两位时、分均补零） |
| **简述** | 主题 | 中文或英文，词间用 `-` 连接，无空格 |

**时间**：取文档**创建时刻**的月、日、时、分（不含年份）。  
**分类**：由**目录**表达（`bugfix/`、`guides/` 等），文件名**不写**类型前缀。

### 各目录示例

| 目录 | 示例文件名 |
|------|------------|
| `bugfix/` | `05-23-1430-导出时间字段丢失.md` |
| `design/` | `05-23-0930-AI分析模块架构.md` |
| `features/` | `05-23-1605-语义去重实施.md` |
| `guides/` | `05-23-1015-定时任务配置.md` |
| `reports/` | `05-23-1800-系统性能分析.md` |
| `updates/` | `05-23-1100-v2.1版本说明.md` |
| `其他/` | `05-23-2045-会议纪要.txt` |

同一分钟、同一目录下若重名，在简述后追加 `-2`、`-3`（如 `05-23-1430-导出优化-2.md`）。

### 禁止

- 不要混用 `YYYY-MM-DD`、类型前缀名（如 `05-23-guide-xxx.md`）、无前缀中文名（如 `修复-xxx.md`）
- 不要用 `14:30`、`14-30` 等非 `HHmm` 的时分写法
- 扩展名：正文用 `.md`；非 Markdown 放 `其他/` 并保留真实扩展名

## 分类标准

### bugfix/

- 修复具体 bug、排障记录、错误修正说明

**内容要点**：问题描述、原因、方案、影响范围、测试验证

### design/

- 新功能设计、架构说明、技术选型、接口设计

**内容要点**：背景、目标、技术方案、架构/流程、接口、风险

### features/

- 新功能/增强说明、用法、实现细节

**内容要点**：概述、场景、步骤、参数、示例、注意事项

### guides/

- 入门、操作手册、配置、最佳实践、FAQ

**内容要点**：受众、前置条件、步骤、常见问题、相关链接

### reports/

- 系统分析、性能测试、代码审查、项目总结、数据统计

**内容要点**：目的、方法、数据、结论与建议

### updates/

- 版本说明、迭代记录、优化与变更日志

**内容要点**：版本、时间、新增/优化/修复、已知问题、升级说明

### 其他/

- 无法归入以上类别或临时文档

---

## 分类冲突时的优先级

多条规则同时命中时，按顺序取**第一条**：

```
bugfix > design > updates > features > guides > reports > 其他
```

**判例**：

- 「修复导出 bug 并优化性能」→ `bugfix/`（修复优先于优化）
- 「v2 新功能使用教程」→ 以主意图为准：偏操作步骤 → `guides/`；偏功能介绍 → `features/`

不确定时**向用户确认**后再落盘。

## AI 自动分类

### 关键词

| 目录 | 关键词 |
|------|--------|
| bugfix/ | 修复、bug、错误、故障 |
| design/ | 设计、架构、方案、技术选型 |
| updates/ | 更新、版本、变更、changelog |
| features/ | 功能、特性、新增、增强、实现 |
| guides/ | 指南、教程、手册、配置、使用 |
| reports/ | 报告、分析、统计、总结、评估 |
| 其他/ | 其他、杂项、临时、备忘 |

注意：`问题` 一词过宽，单独出现时不自动归入 bugfix，需结合「修复/错误/故障」等词。

### 流程

```
分析标题与正文 → 提取关键词 → 按优先级选目录 → 取当前月日时分 → 生成 MM-DD-HHmm-简述.md → 写入 doc/{目录}/
```

生成前向用户确认（可选）：分类、完整文件名、所用模板。
