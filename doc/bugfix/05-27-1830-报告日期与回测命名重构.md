# bugfix · 2026-05-27 18:30 · 报告日期协议错位 + 回测产物命名重构

## 一、症状

主人在评估页点报告级表格的「单报告打分」按钮（截图）：

```
rescore 线程异常: ValueError: 日期格式应为 YYYYMMDD，得到 '2026-05-22'
  File "services/scoring/scoring_service.py", line 688, in rescore_one_report
    score_dates = _eligible_score_dates(...)
  File "services/scoring/scoring_service.py", line 278, in _eligible_score_dates
    sd = next_trade_date(report_date, n)
  File "services/market/trade_date.py", line 172, in next_trade_date
    _ensure_yyyymmdd(date_str)
ValueError: 日期格式应为 YYYYMMDD，得到 '2026-05-22'
```

主人同时观察到回测产物的**文件名错乱**：

```
data/AI_analysis/5月27日/5月27日_18时12分_盘后总结分析报告_backtest_20260522.md
```

——明明是 5 月 22 日的模拟回测，前缀却是「5月27日_18时12分」即真实生成时间，
后缀 `_backtest_20260522` 才是模拟交易日。

## 二、根因（两条相互纠缠的债）

### 债 #1：schema 协议被违反

| 处 | schema 注释 | 实际入库 |
|---|---|---|
| `ai_reports.report_date` | `YYYYMMDD` | `YYYY-MM-DD` |
| `theme_predictions.report_date` | `YYYYMMDD` | `YYYY-MM-DD` |
| `theme_prediction_scores.report_date` | `YYYYMMDD` | （新表暂空） |
| `theme_stock_scores.report_date` | `YYYYMMDD` | （新表暂空） |

源头有两处 `datetime.now().strftime("%Y-%m-%d")`：

- `core/theme_extractor.py::parse_report_meta` — 走 mtime/now 推 `report_date`
- `services/analysis_service.py::_record_ai_report` — 给 `ai_reports.report_date` 用

施工方案文档 [`doc/design/05-27-1213-模板回测功能施工方案v3.1.md`](../design/05-27-1213-模板回测功能施工方案v3.1.md) line 607 早就明确：

> `report_date` 字段格式：v5 统一 YYYYMMDD（在 theme_extractor 入口已规范化，本算法直接用）

但实现一直没对齐，于是积下 16 行错误格式的数据（1 条 ai_reports + 15 条 theme_predictions）。

### 债 #2：回测产物事后 rename + UPDATE 链路脆弱

旧链路 `tools/backtest_prompt.py::_run_analyze_and_mark_backtest`：

1. 调 `AnalysisService.analyze()` 用真实时间命名文件，比如 `5月27日_18时12分_..._.md`
2. 入库 `ai_reports.report_date = today (YYYY-MM-DD)`
3. 调 `_rename_to_backtest` 物理重命名加 `_backtest_{trade_date}` 后缀
4. 显式 UPDATE `ai_reports / theme_predictions SET report_date = 'YYYY-MM-DD'`（模拟交易日）

这条链路有 4 个问题：

- 文件名前缀仍是真实生成时间，对人和程序都误导
- UPDATE 把 `report_date` 强制覆盖为 `'2026-05-22'`（dash 格式），打分链路下游
  调用 `next_trade_date('2026-05-22')` → `_ensure_yyyymmdd` 报错
- 链路太长，rename + UPDATE 任何一步失败都会留半成品
- `_has_existing_backtest` / `_delete_existing_backtest` 也必须把 YYYYMMDD 转 dash 才能匹配，重复绕路

### 隐藏 P1 bug（连带顺手治）

`rescore_range`（GUI「区间重打分」按钮）的 SQL：

```sql
SELECT id, report_date FROM theme_predictions
WHERE report_date BETWEEN ? AND ?
```

传入参数是 `YYYYMMDD`（如 `'20260520'`），表里实际是 `'2026-05-22'`（dash）。
字典序比较时 `'-' (0x2D) < '0' (0x30)`，区间**永远查不到 0 条**，
区间重打分按钮**一直在静默跑空**——但没人报告，因为没报错。

## 三、修方案（治本）

### 命名规则统一

| 场景 | 文件名 | 入库 report_date | is_backtest |
|---|---|---|---|
| AI 分析页生成 | `5月27日/5月27日_18时12分_盘后总结分析报告.md` | `20260527` | 0 |
| 回测 CLI 生成 | `5月22日/5月22日_0时00分_盘后总结分析报告_backtest.md` | `20260522` | 1 |

### 改造点（按调用链）

| 文件 | 改动 |
|---|---|
| `core/ai_news_analyzer.py` | `save_report` / `analyze` 新增 `naming_dt` + `backtest_suffix` 参数；命名时间由调用方驱动 |
| `services/analysis_service.py` | `analyze` 新增 `simulated_trade_date: Optional[str]`；驱动 `naming_dt` + `_record_ai_report` 入库 `is_backtest=1` + `report_date=该日期` + `_maybe_extract_themes` 入库 theme 时同步覆盖 |
| `core/theme_extractor.py` | `parse_report_meta` 优先从文件名前缀正则 `^(\d+)月(\d+)日_(\d+)时(\d+)分_` 解析月日时分；年份从 mtime 兜底；返回 `report_date` 统一 YYYYMMDD |
| `tools/backtest_prompt.py` | **删 `_rename_to_backtest` 函数**；`_run_analyze_and_mark_backtest` 从 80 行 → 30 行薄壳（一行 `svc.analyze(simulated_trade_date=trade_date)`）；`_has_existing_backtest` / `_delete_existing_backtest` 去 dash 转换直接用 YYYYMMDD |
| `services/storage/theme_store.py` | `save_themes` 入口加 `_ensure_yyyymmdd(report_date)` 防御 |
| `services/storage/ai_reports_store.py` | `AIReportsStore.record` 入口同样防御 |
| `services/scoring/scoring_service.py` | `_eligible_score_dates` 入口加 `_ensure_yyyymmdd`；`get_template_eval / get_report_eval` 的 `cutoff_dash` → `cutoff_compact` |

### GUI 显示侧适配

`services/` 层返回 raw YYYYMMDD，`gui/` 层用 helper 转 dash 显示，避免协议
被显示语义污染：

| 文件 | 用途 |
|---|---|
| `gui/utils/date_format.py`（**新建**） | `format_yyyymmdd_to_dash()` / `dash_to_yyyymmdd()` |
| `gui/pages/prompt_eval_page.py` | 上表「最近报告日」/ 下表「报告日期」/ 删除确认弹窗「日期」/ CSV 导出 2 处 |
| `gui/pages/theme_prediction_page.py` | 日期 combo 显示文本（`itemData` 仍是 YYYYMMDD） |

## 七、Hotfix · 2026-05-27 20:00 · 回测多模板互相覆盖

### 7.1 症状

第一版 hotfix 落地后，主人立刻发现新问题：

> 「回测会使用多个提示词测试同一天的数据，现在生成的文件名都一样导致相互覆盖只留下了一个」

例如同一天 `custom_6` 和 `speculator_scalper` 分别跑回测，两次都写到：

```
data/AI_analysis/5月22日/5月22日_0时00分_盘后总结分析报告_backtest.md
```

后写的覆盖先写的，只剩最后一份。

### 7.2 根因

v2 命名规则没把"区分维度"补齐。回测的天然唯一键是 `(template_id, trade_date)`，
而 v2 文件名里只编码了 `trade_date`，丢失了 `template_id`。

### 7.3 修复（v3 终态命名）

| 维度 | v2（5-27 18:30） | v3（5-27 20:00） |
|---|---|---|
| 真实生成 | `5月22日_0时00分_...md` | 同左（不变） |
| 回测 | `5月22日_0时00分_..._backtest.md` ❌ 多模板覆盖 | `5月22日_0时00分_..._backtest_{template_id}.md` ✅ |

**实施点**：

1. `core/ai_news_analyzer.py` · `save_report` / `analyze` 新增 `extra_suffix: str = ""` 参数；
   非空时拼到 `_backtest` 之后，得到 `_backtest_{extra_suffix}`
2. `services/analysis_service.py` · 新增静态方法 `_sanitize_template_id`（仅保留 `[A-Za-z0-9_-]`，截断 64 字符）；
   `analyze` 在 `simulated_trade_date` 分支下把 sanitized `template_id` 作为 `extra_suffix` 透传给 analyzer
3. `tools/migrate_report_date_yyyymmdd.py` · 新增 v2 命名识别正则 `_RE_OLD_BACKTEST_V2`，
   `_scan_rename_plan` 现在同时扫 v1（事后 rename 产物）+ v2（缺 template_id）两种，统一对齐到 v3
4. `_expected_backtest_basename` 增加 `template_id` 形参；从 `ai_reports.prompt_id` 推断

### 7.4 迁移结果

实跑：

```
Step 2 文件重命名（v2 → v3）：
  id=152  rd=20260522  prompt_id=custom_1770292858
    旧: data/AI_analysis/5月22日/5月22日_0时00分_盘后总结分析报告_backtest.md
    新: data/AI_analysis/5月22日/5月22日_0时00分_盘后总结分析报告_backtest_custom_1770292858.md
  ✓ 已重命名（含 ai_reports.file_path + theme_predictions.report_path 同步）

[幂等校验] 再跑一次 dry-run → 0 个待重命名 ✓
```

### 7.5 单元验证

```
✓ save_report 8 个命名分支（真实 / 回测无tpl / 回测+custom_6 / 回测+speculator_scalper / sanitize 中文空格/None 等）全过
✓ 同一天不同 template_id 文件名不再相同（custom_6 vs speculator_scalper）
✓ _sanitize_template_id 对 None / 含中文/空格/@ 的输入正确处理
```

### 7.6 命名规范固化

未来所有回测生成入口**必须**带 `template_id`（CLI `--template` 已强制）；
GUI 触发的回测如果将来支持，也必须保证传 `template_id` 到 `AnalysisService.analyze`，
否则会回退到 v2 命名重新踩坑。

## 八、Hotfix · 2 · 2026-05-27 20:30 · 同模板同日多次跑共存

### 8.1 症状

20:00 hotfix（v3 命名）刚落地，主人立刻提出：

> 「同一天可能使用同一个生成多个」

意思是：同一个 `template_id` 在同一个 `trade_date` 也可能要跑多次
（看 LLM 随机性 / 看 prompt 内部参数微调效果 / 单纯重跑）。
v3 命名 `_backtest_{template_id}.md` 在这种场景下还是会互相覆盖。

更深一层的问题：`tools/backtest_prompt.py` 的 `_has_existing_backtest`
防护逻辑一直是「同 (template, date) 默认 skip，传 `--overwrite` 才删旧重跑」——
**根本不允许多份共存**。本次需要联动放开。

### 8.2 修复（v4 终态命名 + 策略反转）

| 维度 | v3（20:00） | v4（20:30 终态） |
|---|---|---|
| 文件名 | `..._backtest_custom_6.md` ❌ 同模板同日覆盖 | `..._backtest_custom_6_201234.md` ✅（HHMMSS 真实生成时间） |
| `backtest_prompt --overwrite` 不传 | skip 跳过 ❌ 不能多份 | 直接追加 ✅ 多份共存 |
| `backtest_prompt --overwrite` 传 | 同左（删 1 份重写） | 删全部历史版本再写新版本（语义升级为"清空 + 重建"） |

**实施点**：

1. `services/analysis_service.py` · `analyze` 在 `simulated_trade_date` 分支
   把 `extra_suffix` 升级为 `f"{sanitized_tpl}_{now.strftime('%H%M%S')}"`；
   `tpl` 为空时退化为只剩 HHMMSS
2. `tools/backtest_prompt.py` · `backtest_one`：
   - `if _has_existing_backtest(...)` 改为 `if overwrite and _has_existing_backtest(...)`
   - 删除 `else: return skipped=True` 分支
   - argparse `--overwrite` help 文案同步更新（"删全部历史版本"）
   - 模块 docstring 顶部补「20:30 hotfix2 起改为默认追加」
3. `tools/migrate_report_date_yyyymmdd.py` · 把 v3 正则 `_RE_NEW_BACKTEST_V3`
   升级为 `_RE_TERMINAL_BACKTEST`（同时兼容 v3 `_backtest_{tpl}.md` 和 v4
   `_backtest_{tpl}_{HHMMSS}.md`），扫描跳过两种合法终态
4. **数据库无需迁移**：`ai_reports.file_path` UNIQUE 即可，
   `(prompt_id, report_date)` 本来就没有唯一约束
5. `gui/pages/manual_backtest_page.py` · **删除「已存在则覆盖」checkbox**
   （主人随后反馈：该控件默认勾选 + 旧语义反转后变成"清空全部历史版本"，
   会让"同模板同日生成多个"诉求依然失败）。调整：
   - 删 `overwrite_checkbox` 控件创建 + tooltip
   - `_current_inputs()` 删 `"overwrite"` 键
   - `worker = ManualBacktestWorker(... overwrite=False, ...)` 硬编码 False
   - `_on_finished` 清掉永远不会触发的 `overwrite_html` 分支 + 修正 skipped 文案
   - **极少数破坏性清空场景请走 CLI** `python tools/backtest_prompt.py --overwrite`

### 8.3 单元验证

```

✓ 同 date 不同 template → 三层隔离（template + HHMMSS 各自唯一）
✓ template_id=None 兜底 → 后缀只剩 HHMMSS，不会拼出畸形 `__HHMMSS`
✓ 真实生成（simulated_trade_date=None）完全不受影响，extra_suffix=""
✓ backtest_prompt.py 静态检查：`if overwrite and ...` 已切换 + 旧 skip 文案已清干净
✓ 迁移 CLI 幂等：v3/v4 命名都识别为终态，0 个待重命名
```

### 8.4 风险登记

| 风险 | 缓解 |
|---|---|
| 主人误手滑重复点回测 → 自动累积多份消耗 API 费 | 默认追加是主人主动选择（策略 1）；CLI 已加 progress 输出，能看到正在跑 |
| HHMMSS 同秒并撞（理论极小：LLM 单次跑至少几十秒） | 当前不加 IO 兜底；未来真撞了再加序号 |
| 同 (template, date) 下打分查询会拿到"哪一份"？ | `_eligible_score_dates` 按 `report_date` 等值匹配，多份都参与；评估时主人需自行选 file_path |
