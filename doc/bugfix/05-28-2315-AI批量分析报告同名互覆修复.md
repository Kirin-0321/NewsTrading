# AI 批量分析 12 任务只落 3 份报告 · 同名互覆修复

> 日期：2026-05-28 23:15
> 影响版本：05-28-2300 AI 分析页批量模板与队列化上线后立即暴露
> 严重度：🔴 **数据丢失**（12 任务最终只入库 3 条，74% 报告悄无声息消失）

## 一、现象

主人在「AI 分析页」一次选 12 个模板批量跑，全部 worker 都打了 `success` 信号、UI 也亮了 12 个绿勾，但完成后只看到 3 份报告。`data/ai_inference.db` 当日 `ai_reports` 表里只有 3 条记录。

`.huiye/_debug_reports.py` 输出：

```
当日 ai_reports 记录数：3
prompt_id 分布：
  - speculator_scalper: 1
  - custom_1770292858 : 1
  - reverse_thinking  : 1
```

`data/reports/2026-05-28/` 目录下也只有 3 份 md 文件。

## 二、根因

`core/ai_news_analyzer.py::AINewsAnalyzer.save_report` 生成的文件名只到**分钟**精度：

```python
month_day = f"{naming.month}月{naming.day}日"
time_str = f"{naming.hour}时{naming.strftime('%M')}分"
...
report_filename = f"{month_day}_{time_str}_盘后总结分析报告{tail}.md"
```

`tail` 由 `extra_suffix` 决定。**回测路径**（`services/analysis_service.py::AnalysisService.analyze` 在 `simulated_trade_date` 给定时）已经传了 `_{template_id}_{HHMMSS}` 后缀，没问题；但**真实生成路径**（也就是 GUI 批量分析走的这条）`extra_suffix` 始终为 `""`，导致 12 个模板在 23:07 这一分钟内并发完成时全部要写同一个文件名：

```
5月28日_23时07分_盘后总结分析报告.md
```

结果：

1. **磁盘**：后写的覆盖先写的，最终只剩 1 份 md（如果同分钟全部生成）。
2. **数据库**：`ai_reports.file_path` 上有 `UNIQUE` 约束，第 2 个及之后的 `INSERT` 直接抛 `IntegrityError`，被 service 层吞掉只在日志里报错，UI 看不到。
3. **UI**：12 个 worker 都收到 `success`（worker 不查 DB），所以 UI 全亮绿勾，但人去翻报告时发现只有 3 份。

3 份能存活是因为它们恰好分散在 3 个不同分钟（23:07、23:08、23:09 各 1 个）。

## 三、修复

把 `extra_suffix` 的赋值从 `if simulated_trade_date:` 块里挪出来，**所有路径**都加 `{template_id}_{HHMMSS}` 后缀。

文件：`services/analysis_service.py`，方法 `AnalysisService.analyze`，行号约 137–172（修复后）。

### Before

```python
naming_dt: Optional[datetime] = None
backtest_suffix = False
extra_suffix = ""              # ← 真实生成路径永远为空
if simulated_trade_date:
    ...
    backtest_suffix = True
    sanitized_tpl = self._sanitize_template_id(template_id)
    run_stamp = datetime.now().strftime("%H%M%S")
    extra_suffix = (
        f"{sanitized_tpl}_{run_stamp}"
        if sanitized_tpl else run_stamp
    )
```

### After

```python
naming_dt: Optional[datetime] = None
backtest_suffix = False
sanitized_tpl = self._sanitize_template_id(template_id)
run_stamp = datetime.now().strftime("%H%M%S")
extra_suffix = (                # ← 提到 if 外，真实生成 / 回测都享受
    f"{sanitized_tpl}_{run_stamp}"
    if sanitized_tpl else run_stamp
)
if simulated_trade_date:
    if not (...校验): return out
    naming_dt = datetime.strptime(simulated_trade_date + "0000", "%Y%m%d%H%M")
    backtest_suffix = True
```

### 修复后文件名形态

| 路径 | 文件名 |
|---|---|
| 真实生成（batch 中第 N 个完成） | `5月28日_23时07分_盘后总结分析报告_custom_6_230751.md` |
| 回测产物（保持原样） | `5月22日_0时00分_盘后总结分析报告_backtest_custom_6_195810.md` |

`save_report` 内部 `tail` 拼装逻辑无需改动（`elif extra_suffix: tail = f"_{extra_suffix}"`），原本就能消化新值。

## 四、影响面与兼容性

- ✅ **回测路径**：行为完全不变（之前已经填 `extra_suffix`，挪出 `if` 块后该路径还会立即被回测分支覆盖前的代码路径覆盖；实际行为 = 旧逻辑）。
- ✅ **真实生成路径**：新文件名带后缀，旧报告（命名只到分钟）继续可读，不影响检索。
- ✅ **数据库**：`ai_reports.file_path UNIQUE` 不再被并发任务踩中。
- ⚪ **极端边界**：同模板同秒并发 2 次（人为双击 / 脚本极速重提）仍可能撞名，但日常 GUI 操作触不到，且 service 层 `IntegrityError` 现在只损失 1 条而非 N-1 条，可接受。

## 五、验证

- 静态：mypy / flake8 通过（`services/analysis_service.py` 无新增 lint）
- 动态：下次主人手动批量跑一次（≥5 模板）观察 `data/reports/{today}/` 目录和 `ai_reports` 表记录数是否相等

## 六、遗留待办

- 已损坏的 9 份「23 时 X 分」报告已永久丢失（磁盘被覆盖、DB 未入库）；如需重跑，主人在分析页重新选 9 个模板再来一遍即可，本次修复后不会再撞
- `core/ai_news_analyzer.py::save_report` 长远应该把文件名精度直接提到秒级，并把 `extra_suffix` 拼装责任收回到 core 层而不是让 service 算 `HHMMSS`，作为后续重构 TODO，**本次不动**（KISS）
