# 05-26 22:40 — 连板梯队 / 涨停时间在 kpl_list 延迟时全空修复

> ⚠️ **2026-05-27 18:10 更新**：本文 v1+v2 修复方案的核心局限——「假设 `limit_list_d` 已落库、仅 `cons_nums` NULL」——已被 [涨停数据三源融合 v1](../updates/05-27-1810-涨停三源融合上线.md) 彻底解决：接入同花顺 `limit_list_ths` 作为 T 日主源后，T 日盘后 16 点即有完整 64 只涨停数据，不再依赖东财/开盘啦的 T+1 延迟。本文档保留作为历史记录；**未来类似"全空"问题不会再发生**（除非同花顺也延迟，概率极低）。


## 现象

GUI「🚀 涨停 & 连板」Tab 在 20260526 当日完全空白：4 个桶
（首板 / 2 连板 / 3 连板 / 4 连板及以上）都显示 0 只股，但市场实际
当日有 46 只涨停股、24 只炸板股、16 只跌停股。

## 根因

### 根因 1（数据源）：Tushare `kpl_list` 接口当日延迟

```text
> 现在调 kpl_list(20260526, tag=涨停)  →  返回 0 行
> 对比 20260525 含 cons_nums 的 U 股数  →  103 只（完整）
```

`kpl_list` 接口在 T 日（盘后）经常延迟到 T+1 才有数据，所以
`fact_limit_stock.cons_nums / status / theme / lu_time` 当日全 NULL。

### 根因 2（连锁 bug — 真正让 GUI 空白的元凶）

`services/market/service.py:555` 在读取 ladder 数据时加了：

```sql
WHERE trade_date = ? AND limit_type = 'U'
  AND cons_nums IS NOT NULL    -- ⚠️ 这一行
```

本意是过滤掉未识别的脏数据，但**当 kpl_list 延迟时**：
* `limit_list_d` 已经拉到了 46 只涨停股写入 `fact_limit_stock`
* 但这些股的 `cons_nums` 还是 NULL（等 `kpl_list` 来合并）
* 所以这个过滤把它们全部丢掉了

讽刺的是 `build_limit_ladder` 内部的 `parse_cons_nums` 本来有 4 层兜底
（cons_nums → status → 首板/首日 → 1），完全能处理 NULL 输入，但 SQL
在它收到数据前就把数据过滤光了。

### 根因 3（隐性 bug — 同时修复）

`service.py:552` 的 SQL 字段：

```sql
SELECT ..., limit_up_time, open_times
```

但 `build_limit_ladder` 第 179 行取的是：

```python
"lu_time": raw.get("lu_time") or raw.get("first_time") or ""
```

字段名对不上，所以即使是 `kpl_list` 数据完整的日子，GUI ladder 的
「涨停时间」列也始终为空 —— 这个 bug 一直存在，未被发现。

### 根因 4（gaps 注入 bug — 顺手修）

`service.py:318` 的 `summary["gaps"] = quality.get("gaps") or gaps` 用了
`or` 短路逻辑：validator 的 gaps 非空时会**完全覆盖**手动 collect 的 gaps，
导致 `_read_breadth_and_sentiment` 等内部收集的 gap 提示不会出现在
`summary["gaps"]` 里 —— 与 GUI 数据质量组的「gaps/conflicts」面板割裂。

## 改动

### 修复
- **`services/market/service.py` `_read_breadth_and_sentiment`** —
  去掉 SQL 过滤条件 `AND cons_nums IS NOT NULL`；SQL alias
  `limit_up_time AS lu_time`；当 `u_cnt > 0 AND cons_nums_filled == 0` 时
  追加 gap 提示
- **`services/market/service.py` build() 第 318 行** — `gaps` 合并改为
  按 `field` 去重的合并（validator 优先），不再用 `or` 短路覆盖

### 数据
- 20260526 单日 force-refresh 重跑（耗时 49.4s，1 次 API + 2 次 AI 调用），
  `market_summaries[20260526].limit_ladder.首板` 从 0 → 46

# v2 — 历史递归推算连板数 + theme 兜底

## 起因

主人 22:48 反馈："为什么只有首板，二连板可以通过昨天的涨停与今天的涨停
计算出来，同理三板四板，最多算到 7 板，一个简单的递归查询就行"

切中要害——v1 的 fallback 让所有 46 只股都归首板，但 `fact_limit_stock`
里已经有完整的 30 天涨停历史，**完全可以靠"T 日涨停 + T-1 日仍涨停 → 2 板"
递归推算**。

## 算法

```text
T 日所有 U 股 = {ts_code₁, ts_code₂, ...}
默认 cons_nums = 1（首板）

for step in 2..max_n (默认 7):
    prev_date = dim_trade_calendar[curr_date].pretrade_date
    交集 = (T 日 U 股) ∩ (prev_date 仍是 U 股)
    for c in 交集: cons_nums[c] = step
    curr_date = prev_date; 当前关注集 = 交集
    if 交集为空: 提前 break
```

性能：每个 step 一次 `IN` 查询，46 只股 7 步 = 最多 7 次 SQL，<100ms。

## theme 兜底

连板股在 T-1/T-2 日必然有完整的 `theme`（kpl_list 早就出过），
所以对 NULL theme 的股回溯最近 5 个交易日找最新的 theme 直接复用。
首板股因为是新涨停，历史日没 theme，命中率天然低（符合预期）。

## 改动

### 新增（service.py）
- `_derive_cons_nums_from_history(conn, td, ts_codes, max_n=7)` —— 静态方法，
  纯历史递归，零 API 成本
- `_derive_themes_from_history(conn, td, ts_codes, lookback_days=5)` —— 同上，
  按 `ORDER BY ts_code, trade_date DESC` 取每只股最近一次有 theme 的记录

### 修改（service.py `_read_breadth_and_sentiment`）
- 拆分 `null_cons_codes` / `null_theme_codes`
- 当任一非空时调用对应 derive 函数
- 写回 `kpl_dicts` in-place，同时打 `cons_nums_source` / `theme_source` 标记
  （审计元数据，不进 ladder 桶；下游需要时按需读）
- gap 提示从「全归首板」改为「已基于历史递归推算 + 分布详情」

## v2 局限

- 首板股的 theme 仍有 76% 缺失（首板=新涨停股，无历史 theme，无解）
- 连板数最高到 7 板（max_n 参数，可调；30 天数据足够 7 板递归）
- 当 `dim_trade_calendar.pretrade_date` 链断裂时递归提前 break（已防御）
- T+1 真实 kpl_list 数据出来后 force-refresh 会覆盖派生数据（这是设计意图）
